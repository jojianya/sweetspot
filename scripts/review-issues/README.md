# Review → GitHub issues

Turns the findings in [`CODE_REVIEW.md`](../../docs/CODE_REVIEW.md) into
labelled, milestone-assigned GitHub issues.

## Files

| File | Purpose |
|---|---|
| `generate.py` | Parses `CODE_REVIEW.md` → one markdown body per issue + `manifest.json` |
| `create.sh` | Uses `gh` to create milestones, labels and issues from the manifest |
| `bodies/` | Generated issue bodies (safe to delete, regenerated by `generate.py`) |
| `manifest.json` | Issue titles, labels, milestones, ordering |
| `created.txt` | Log of issues created by the last real run |

## Usage

```bash
# one-time auth
gh auth login --hostname github.com --git-protocol https --web

# preview (no auth needed, no writes)
python3 scripts/review-issues/generate.py
./scripts/review-issues/create.sh --dry-run

# for real
./scripts/review-issues/create.sh
```

## Structure

- **38 individual issues** for every P0 / P1 / P2 finding (4 + 10 + 24)
- **5 themed issues** for the 23 P3 polish items, grouped as
  client-perf, a11y, tests/CI, dead code, and consistency
- **4 milestones**: `P0-critical`, `P1-high`, `P2-medium`, `P3-polish`
- **11 labels** created on top of GitHub's defaults: priority tiers plus
  `backend`, `frontend`, `security`, `performance`, `sql`, `devops`,
  `needs-design`

## Idempotency

`create.sh` skips milestones, labels and issues that already exist (matched on
title), so it is safe to re-run after a partial failure without creating
duplicates.

## After filing

Commit `docs/CODE_REVIEW.md` to `development` so the `See CODE_REVIEW.md`
permalinks in each issue resolve. They point at
`blob/development/docs/CODE_REVIEW.md`, which 404s until that file is pushed.

If `docs/CODE_REVIEW.md` is ever moved again, the permalinks baked into the
already-filed issues go stale. Re-run `generate.py` and update the live issue
bodies rather than assuming the links still hold.
